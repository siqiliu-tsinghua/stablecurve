# FABER 持久化与缓存重新设计

初稿：2026-11-08；更新：2026-11-09。基线：v0.3.0。状态：生产缓存已实现，本轮按合理工作集收口；极低预算规划性能仍有限制，当前范围见第 1.6 节。

审查依据见 [回退前审查报告](archive/2026-11-08-faber-cache-review.md)。本轮设计从回退至 v0.3.0 的源码重新开始，不以回退前的 `managed` 执行器为默认实现起点。

## 1. 目标和不可破坏的行为

1. 内存充足、依赖已常驻时，保留原来的数学索引、整数 ID、连续求和块、整方程合并和直接结果表。数学乘加循环不查询数据库、不逐项加锁、不逐值更新引用计数或命中统计。
2. 同一实例的已完成结果跨查询保留，只有内存压力才触发淘汰。重复不同但共享后代的查询必须真正复用 L1。
3. 所有实际完成、可独立复用的积分结果均进入 SQLite 持久化，包括纯 ψ、Hodge 后代、κ/ψ/λ/ch 的混合和公共积分结果；范围不受 v0.3.0 是否已经为它建立 memo 的限制。高价值结构和完成数学子结果也纳入支持范围，按下列数据目录分级接入。临时算术量与未完成计划单独管理。
4. 计算线程把结果写入原有数学 L1，并在原有层/批次写回边界标记完成。存储线程主动取得已完成结果，自行复制、编码、组批和提交；计算线程不为持久化克隆 Q、组装结果包或入队。
5. 内存管理按批次、向量扩容和连续块记账，使用可伸缩的统一预算；不按图、索引、项块固定切出互不借用的硬份额。
6. 无持久缓存模式保持真正的内存计算。正常查询不建立 SQLite TEMP 工作图；出现真实压力时才启用独立的块溢写机制。
7. 精确结果、跨查询复用、实际内存和性能分别验收。前一阶段未达到目标，不继续用更多机制掩盖差额。
8. 缓存是原计算器的附加能力。常驻路径无明显性能回归是放行条件，不给新增机制分别分配可累加的减速额度。冷算以保持效率为目标，复用场景以减少重算为目标，受压/恢复场景以安全完成和复用成果为目标。

### 1.1 必须持久化的完成积分

| 范围 | 保存内容及复用关系 |
|---|---|
| 公共积分入口 | 实际请求的纯 λ、纯 ψ、κ–ψ、λ–ψ、ch–ψ，以及 κ/ψ/λ/ch 的一般混合积分；保存最终精确值 |
| Hodge 后代递归 | 全部实际求出的、具有独立规范数学身份的后代子积分，不仅保存根答案 |
| 纯 ψ 递归 | λ/ch/κ 混合计算中产生的纯 ψ 子积分，以及直接 ψ/Tau/ST 路径求出的合法积分；相同数学状态应跨入口、跨查询、跨线程数复用 |
| 图类积分 | DR、Chiodo、Witten、超椭圆等入口已经完成的标量积分，以及其中实际求出的顶点/装饰积分 |
| 直接公式和零值 | 直接公式得到的公共答案、已完成合法积分的零值同样属于成果；零不能表示缓存缺失 |

完成标记须覆盖串行记忆化、并行完成批和公共入口/直接公式三条路径。存储线程通过相应缓存的完成目录读取，不能只扫描并行 `evaluate_layers`，导致单线程、小规模或公式捷径漏存。

κ 分划和 λ 展开产生的组合系数与子积分分开。保存子积分本身的值；符号、重数、Bernoulli 因子等外层系数不混入子积分键对应的数值。为填满缓存而额外求积分、物化所有 string/dilaton 别名或枚举未访问状态，不属于本方案。

### 1.2 归一化和稳定数学键

内部后代状态的参数虽然名为 `ch`，实际表示奇数指标的

```text
C_m = (m+1)! · ch_m / B_(m+1)
J_C(g; d; c) = ∫ Π ψ_i^d_i · Π C_m^c_m
```

入口已把相应 Bernoulli 因子提出。纯 ψ 就是 `c` 为空；从不同 λ/ch/κ 查询到达的同一 `J_C` 必须共用缓存。例：`C_1 = 12 λ_1`，内部 C 积分不能直接当成真实 ch/λ 积分读回。真实类积分、归一化 C 积分及辅助递归约定使用明确的值语义。

规范键包含数据种类、数学语义约定及完整自然参数。后代键显式保留 `g`、`n`、完整 ψ 次数列表和合并后的 C 指标/幂；零次标记不能丢失。普通对称积分可排序 ψ 次数；DR 权重、标记装饰等额外数据必须同时保留对应关系，不能单独排序 ψ 后错误合并。

历史 `st_recur([])=1` 是辅助递归约定，不等同于合法稳定模空间上的纯 ψ 值。旧 ST 数据只在确认输入语义一致时适配到统一积分缓存；辅助约定保留独立类型，不能无条件合并命名空间。

### 1.3 其他高复用对象

持久化范围不以“是否是最终积分”划线。具备稳定输入、重建昂贵、能跨查询或跨进程复用的完整数学对象，应有自己的缓存类型。除完成积分必存外，下列结构按实际重建成本、载入成本、体积及复用频率选择启用；不会为了保存而提前生成未请求的数据。

| 对象 | 策略与粒度 | 完整数学身份及依据 |
|---|---|---|
| 完整稳定图层 | 高优先级候选；按层/层内块保存 | `(g,n,余维,表示约定)`；`generators::LAYERS` 的枚举和同构归并可被 DR/Witten/GRR 反复复用。保留标记关系和必要的层内顺序；它与 Hodge 递归计划是两类对象 |
| 已求出的图自同构数 | 可附在图记录上保存 | 完整图及标记约定；不为缓存预先计算整层尚未用到的自同构数 |
| 通用符号多项式 | 高优先级候选；整多项式/整表保存 | 如 Chiodo `edge_coeff(e1,e2)` 和 Witten `pm_poly(d)`；已有 `flow::SharedTable` 负责跨图、跨线程 L1 复用，L2 接在其未命中/完成边界 |
| 昂贵的完成图级标量 | 高优先级候选；按独立数学状态保存 | 如平衡流求和与插值的 `Q(0)`；持久键须包含图、顶点给定量、对应边指数及归一化约定。不能照搬图闭包内只含 `exps` 的局部键 |
| 数值边因子整表 | 按重建/载入收益选择 | DR `(s,m)`、Chiodo `(e1,e2,m,spin)`、Witten `(d1,d2,m)`；保存整张 `Vec<Q>`，不逐表项执行 SQL |
| λ→ch 展开、κ 分划/分配模板 | 先复用 L1；高阶或重建昂贵且常用时整块持久化 | 基础 λ 展开依赖阶数，组合展开还依赖完整指数；κ 模板保留重数、顶点数等全部隐含参数；不能把仅供某个闭包使用的简化键直接外推 |
| 已完成的类或规范多项式输出 | 有明确跨查询收益时保存 | 保留生成参数、标记和表示约定；流式积分不能为了缓存先物化完整类 |
| Bernoulli、阶乘、双阶乘、二项式、GRR 因子、单点 ψ 表 | 默认使用紧凑 L1 表 | 常用范围内小且容易扩展；高频使用本身不构成逐项落盘理由。大指标下若值得跨会话复用，再测整表保存 |
| `FlowTopology`、插值权重、小型局部模板 | 默认 L1/查询内复用 | 从已有图或少量参数重建通常便宜，读盘未必合算 |

稳定图层、DR/Witten 公式表通常不参与 λ₁ 顶次积分的直接 GRR 后代路径。扩展这些对象的持久化不能替代对 g=20 主线内存问题的解决。

### 1.4 临时工作区与写入优先级

临时多项式乘积、逐项贡献、部分和、当前任务队列、运行时 ID 和未执行 `Plan/TermBlock`，默认作为工作区管理；内存压力时可以整块溢写，需要恢复执行进度时才按独立断点方案保存。已完成的可复用对象与尚未完成的计算现场不能混为同一种持久缓存。

额外结构对象在原有缓存中标记完成，后台通过独立适配器主动读取并编码逻辑字段，不直接保存 Rust 指针、锁、`Rc/Arc` 内存布局或进程局部 ID。后台持有和延寿空间单独计账、测量；不能为统一持久化而把计算器中的所有结构重新包装成一种对象。

积分写批优先于可选的大结构对象；大对象分块处理，避免长时间挡住积分提交。积分批按自身 FIFO 顺序推进提交水位，结构对象单独记录完成状态，不能让低优先级对象阻塞积分耐久确认。只有完整对象/完整单元提交后才作为可复用缓存返回。

结构对象默认低优先级后台保存，不在普通数学返回前自动设置持久化屏障。显式要求持久化完成时，屏障覆盖此前完成积分及策略选中的结构对象；另行记录二者的完成时间和会话收尾时间。结构缓存的成本必须验收，不能靠提前返回宣称全部工作已经完成。

### 1.5 计算流程的保护边界

| 情况 | 应保持的行为 |
|---|---|
| 未启用持久化、内存充足 | 沿用原数学路径；不创建存储线程、持久化完成目录、SQLite 工作图或后台扫描任务 |
| 启用持久化、数据常驻且无压力 | 原查找、展开、合并、调度和乘加照常执行；计算侧只在原写回边界标记完成，后台自行追赶 |
| L1 命中且没有新完成项 | 不推进新完成水位，不重复持久化、不产生空事务或额外存储等待 |
| 真正的内存压力或恢复缺失 | 才启用冷数据回收、缺页准备、块溢写、压缩及必要等待；不提前给常驻路径增加逐项处理 |

后台读取结果和数学索引也会占用锁、处理器、带宽和分配器，必须算作新增成本。不得让“主动拉取”变成每层全表扫描，或让读取目录长期挡住原有写回。任何为了缓存改变结果布局、串行递归访问、调用线程并发能力或结构所有权的步骤，都要独立通过回归门槛。

### 1.6 2026-11-09：本轮范围收口

目标是在合理工作集和实际生产预算下保持计算效率、控制内存并复用已提交成果。SQLite 持久化和有限工作块溢写不保证任意规模查询能在任意低预算下完成；不再持续降低预算，以迫使所有测试完成。

本轮保留紧凑方程目录、准入记账与有界重试修复、已有工作块溢写和已提交积分恢复。GNU Linux 在存储线程的既有压力巡检边界尝试归还分配器空闲页，随后重新采样；普通路径不调用，也不据此凭空增加预算额度。

本轮撤回规划完成后在压力下清空数学索引的实验策略，保留原查找映射和跨查询 L1 复用。活动结果表、反向目录及仍需使用的数学索引构成当前后端的常驻工作集；不继续实现活动值表分页、反向目录外存、换出调度、代际压缩或新的分段求和执行器。

资源不足时明确报错仍是接口要求，但当前低预算规划可能长时间重试，尚未实现对任意输入的及时拒绝。g=16 的收缩前实验暴露了这种局限，见第 10 节；不把受控内存、测试超时或停滞错误算作积分完成，也不据此声称相应预算在数学上不可行。

开发验收限定在已授权的小样本、精确值、持久化恢复和常驻性能回归。实际生产规模及预算由用户在生产环境验证；后续只有真实生产条件仍存在问题时，再讨论独立的架构调整。本决定不新增 g=18/20 开发机验收任务。下文历史计划和实验记录保留为依据，后续实施范围以本节为准。

## 2. 保留原计算核心，只接入三个边界

v0.3.0 的核心是 `Engine`、`Plan`、`Built`、`TermBlock` 和 `evaluate_layers`。继续先对方程 `collect`，再将一个展开批次合并成连续 `TermBlock`；保留原分层并行和直接整数索引求值。

新增接口限定在：

| 边界 | 工作 |
|---|---|
| 发现前沿/展开批次 | 既有数学身份在实例目录中可定位；存储线程自行读取；恢复场景下批量查找 L2 |
| 完成层/批次 | 按原算法写回数学 L1，发布完成范围/完成标记；存储线程主动读取新增完成项 |
| 批次之间及容器扩容 | 读取后台发布的额度，必要时进入压力慢路径；系统内存采样和大批回收不进入逐项计算 |

旧计算核心只增加这些边界接口，不再为每个方程增加一套常驻 `Record`、带锁的块树和数据库状态。

## 3. 所有权、实例和并行

### 实例内 L1

每个实例必须具有明确的数据与存储归属，查询结束释放本次计划和临时项，保留数学 L1。首个接入里程碑沿用 v0.3.0 的调用线程计算上下文，提供独立于查询栈的结果读取口；实例和存储服务可以登记多个计算结果源。不得为了接入后台读取，先把所有调用线程统一到一张被顶层查询锁独占的结果表。

Hodge 后代、ST/IC 等数学记忆化均须有明确的实例和预算归属；预计算系数表作为另一类工作区统计，保持适合各自数学用途的表示。

v0.3.0 的跨查询复用实际限于同一调用线程；Python `FABER` 本来是 `unsendable` 且方法独占借用实例，不能声称它已有同实例跨线程并发。必须保留原 Rust 多调用线程和各查询内部的并行能力。迁移 `thread_local` 所有权、实例隔离适配、跨上下文共享数学结果及任何新增顶层排队，都属于需要分别设计、单独验收的改动；本方案撤回“默认给每实例加一把顶层查询排队令牌”的决定。

### 存储线程主动读取

第一版保留 `Vec<Q>` 的直接读取。计算线程完成原有写回后，只发布“哪些层/批次/槽位已经完成”的元数据；存储线程以自己的读取游标主动发现新增完成项。计算线程不执行持久化所需的 Q 克隆、结果批组装、编码或入队。通知只用于唤醒，正确性以可重复读取的完成目录为准，不能依赖不丢失的消息队列。

Hodge 完成目录优先复用原 `Plan.layers`、批次 ID 清单和已有数学索引，按层/批次发布完成范围，不为每个求和项增加原子操作，也不要求结果 ID 按完成顺序连续。目录的寿命与求和项块分开，不能为了让后台找到结果而延长整张 `Plan` 的寿命。其他数学缓存和完整结构对象提供同样的完成状态及只读访问口，不强制采用同一种内部表示。

v0.3.0 的并行求值已有结果表读写锁：工作任务持只读视图，协调者在写回边界取得写访问。新设计将这一个结果表级访问口保留为可被存储线程安全读取的实例对象，数据仍为连续 `Vec<Q>`，不改成逐值 `Arc<Q>`；其生命周期独立于一次函数调用的栈帧。单线程路径同样在层/批次边界提供短访问窗口，不能持有整次查询的独占访问而让后台一直等到查询结束。

存储线程先从完成目录选择一小批已完成、尚未持久化的 ID，在自己的预算内取得缓冲空间，再短时读取结果源。当前并行后代实现直接借用原 Q，在有界窗口内编码后释放读取访问，不创建 Q 副本或逐条身份向量；其他结果源可由后台小批复制后编码。组批和 SQL 均由存储线程完成。计算工作线程与存储线程可以并行读取已完成值；计算侧的扩容、写回、淘汰和压缩只能在安全的写访问下进行。

存储线程只保留实例数据视图和必要的生命周期持有关系，不持有顶层查询入口令牌；计算线程等待提交前必须释放结果表写访问。禁止持结果表锁等待预算、SQL 或提交，也禁止让存储线程反过来等待计算线程为它创建结果包。读取批的大小与持读访问的时长需实测限制，计算侧写回的等待必须单独记录，不能把它藏在“后台异步”描述里。

计算写回、扩容和索引更新优先于后台采集。后台使用可退让/非阻塞的读取尝试，限制每个窗口的字节量与持有时长；遇到计算侧写回意图时不再开始新的读取窗口，先处理自己的编码和提交。不得通过连续重取读锁饿死计算写回，也不能仅凭 `RwLock` 的名字假定各平台已经提供所需公平性。必要的写回状态只在原批次边界表达，不增加逐值或逐依赖同步。

写回优先只在对应结果源已具备必要资源、即将实际写入时表达，不是贯穿整个计算批的排他状态。计算进入预算、缺页或提交等待前，必须撤销写回意图及排他领取，释放源访问并允许后台继续读取；否则会形成“计算等提交、后台等写回”的进展死锁，即使双方都未持锁也无法解除。优先级按具体结果源生效，某一源的写回不能阻止其他源的后台取数。

访问顺序为：后台取得缓冲额度，短时读取/领取完成目录并释放目录访问，然后读取结果源；并行后代可在短读取窗口内直接编码，释放源访问后才执行 SQL 或等待预算。回收方需先排除正在读取的对象，再在安全写访问下回收；目录与源访问不反向嵌套。后台释放源读取持有关系后，L1 的 dirty 保护仍持续到提交确认。

后台额度不足时，不能持领取状态或源引用等待只能由自己解除的空间。应先放弃尚未处理的领取、处理已有缓冲并推进提交，再重试；编码、提交和回读保留最小进展额度。预算总账锁内不得调用缓存回收、获取结果源锁或等待其他实例。

数学身份利用已有整数 ID、数学索引和既有 `State` 批提供只读定位；存储线程自己生成规范键，并维护“引擎会话、代际、ID → 规范键或存储位置”的存储目录。原始状态批延长生命周期、后台取数缓冲和键目录的空间均记入预算，不由计算线程另建第二套待写结果容器。

原数学索引主要是“键 → ID”，不能假定已经存在高效的反向目录。后台身份发现必须增量推进：复用既有层/次数分片及新增范围，或读取已有不可变状态清单，建立有预算的 ID 定位目录。禁止每完成一层或每轮轮询重扫全部历史索引；扫描应尽量避开规划器正在修改的分片，不能长期持读访问挡住插入。这部分 CPU、空间和锁竞争全部计入后台取数对照，不能藏到真实 SQLite 阶段才出现。

只有身份已经转移到可回读的定位元数据后，才能释放对应原始状态批。只要活动计划还引用该 ID，定位关系就必须保留。当前反向目录驻留内存，其容量计入工作集；本轮不实现目录外存，也不保存另一份可查询的待写数学值。

这里需要实验决定的是存储线程内部如何短时取数、缓冲和编码，以及这种读取对原有写回的影响；“由计算线程复制和交接结果”已经排除。初始原型采用后台小批复制后立即释放读取访问；后续并行后代改为存储侧短窗口直接编码，避免 Q 克隆和逐条身份分配，不改变计算线程的职责。

### 串行缓存与结构对象的读取口

原 `Descendents::eval`、ST/IC 的线程局部 `RefCell` 递归缓存不具备并行结果表同样的读取口。其安全可见边界必须先做独立原型；不能未经测量便给每次 memo 读写加存储同步，也不能把整次递归套在独占锁内，等查询结束后才让存储读取。接入须保留原递归算法，通过单线程小规模、公式和高命中负载的回归门槛；未通过不扩展到全部递归模块，更不能统一改用另一执行器。

`flow::SharedTable` 已完成的 `Arc<V>` 适合由后台按对象取得只读持有关系。`generators::LAYERS` 中的 `Rc/RefCell` 则不能直接跨线程读取；接入时应给完整图层提供可共享的外层所有权和完成目录，按对象/层改变读取口，而不是给每个 Q 或图节点添加引用计数。默认仅 L1 的小表不因本方案而强行改成跨线程源。

## 4. 完成结果生命周期：消除待写值索引

```text
计算完成并进入数学 L1
        ↓
发布完成范围/标记 ready_seq
        ↓
存储线程主动读取新增完成项，在自己的有界缓冲中取数
        ↓
后台编码、批量事务提交
        ↓
提交确认推进 durable_seq
        ↓
结果仍保留在 L1；有压力且没有任务正在使用时才可淘汰
```

发布完成标记前，结果及其身份必须已经写入可安全读取的数学 L1。完成范围使用 Release/Acquire 或相应锁同步发布与读取；结果源访问还需保证读取期间不会扩容搬迁、淘汰或压缩。不能仅凭“标记为完成”就在并发扩容的裸 `Vec` 上保存指针。合法零值具有同样的完成状态，预分配的零槽不属于完成结果。

查询因错误提前退出时，应依据完成目录保留已完成成果，清除或隔离本代尚未完成的索引/槽位；下一次查询不能把未求值的零槽当成真实零值命中。

从标记完成到提交确认的 dirty 结果始终保留在数学 L1，包括存储线程尚未发现或尚未复制的部分；计算任务和后台读取期间所用对象均保持有效。因此后台不需要可查询的 pending `BTreeMap`。受限的是整个未提交积压的字节量，不能只统计后台已经复制出来的一小段。

上述 dirty/提交规则只适用于启用持久化的模式。关闭持久化时没有提交水位可等待：本次计划不再需要的完成值可以回收，仍会再次使用的值必须保留或先获得明确允许的临时后备。临时后备不提供跨崩溃耐久保证；若禁止溢写且活动工作集无法容纳，应返回资源不足。无压力时该模式不启动 SQLite 工作区。

完成目录保留发布水位 `ready_seq`，存储服务保留读取游标和提交水位 `durable_seq`。提交水位表示该水位之前的完成范围均已提交，不等于向量下标。存储线程按完成范围顺序拉取，事务成功后推进连续提交水位；结构对象使用自己的完成状态，避免每个值一个原子状态。重开数据库读回的结果直接属于已持久化数据。

### 数学返回与持久化确认分开

普通计算调用在数学结果可用、完成标记已发布后返回，不隐式等待 SQLite。该返回仅表示数学计算成功，不表示刚产生的成果已经全部落盘。此前计划自行加入的“每次查询返回前自动 flush”撤回；它尤其会使短公式查询等待与计算无关的磁盘延迟。

需要耐久确认时，由独立的显式 `flush`/等待接口快照积分目录、结构目录的发布水位和保存策略。后台须先扫描到目标水位，再自行取完并提交；不能用“后台已经取走/挑选的对象”代替完成边界。`flush(target_ready_seq, target_object_ready_seq, policy)` 成功才表示该范围内的成果已提交。没有新完成项、目标已提交时立即完成，不额外执行 SQL 或空事务。

正常会话结束、显式 `close` 和 CLI 正常退出需等待相应持久化边界；调用者可选择明确的“计算并等待持久化”操作，但不得把它与普通计算返回混称同一种耗时。必须提供能够报告异步错误的显式关闭/状态接口，不能只依赖无法正常返回错误的析构路径。

写失败时公开失败状态并唤醒全部等待方。已知故障须在后续计算交互、显式等待或关闭中报告，不静默宣称已持久化；正在等待内存/提交进展的计算不能永久挂起。已经返回的数学值仍是计算成果，不能追溯宣称其持久化成功。

异步批量写保留用户已接受的有界未提交窗口。进程被杀或掉电后复用已经提交的完成值；未提交批可能重算。恢复未完成计算计划是另一层能力，不能把结果缓存恢复描述成整个执行现场无损恢复。

未提交窗口包含尚未被后台复制的全部 L1 dirty 数据，不以取数缓冲大小代替。默认由统一内存上限和进展预留约束积压，另行报告 dirty 字节峰值、最老未提交年龄与最终排空时间；不暗中用固定小队列或严格时间上限在大量空闲内存下停算。若另加独立的最大损失量/最长未提交时间约束，它可能触发额外等待，必须作为显式策略说明。

## 5. 真正按内存压力管理

### 总预算

从当前进程占用、系统可用物理内存和提交余量、运行环境限制及用户上限生成进程总预算，并预留系统、算术临时空间和分配器余量。多个实例共用总账，不能各自重复领取整台机器的可用内存。

同时记录以下构成及实际工作集/私有提交内存：

- 结果槽位、结果大整数堆和数学索引；
- 方程、层索引及尚未求值的连续项块；
- 并行工作批和临时算术空间；
- 数学 L1 中尚未被后台取走/提交的完成结果、后台取数副本、状态描述与键目录；
- SQLite 缓存及运行时余量。

dirty 是结果缓存中的状态子集，pin/读取持有关系只改变可回收性，同一份 L1 数据只计一次。后台副本、编码缓冲和额外目录才增加占用，不能将共享原值或每次 pin 重复收取数据额度。

额度估算与实际进程内存分开报告。警戒线、硬上限和回收目标具有滞回区间，并随可用内存收紧；其初值需要测量，不能把某个百分比当作已证实的最优值。

系统内存采样和策略维护由后台完成，计算侧在既有批次/扩容边界读取额度并进入必要慢路径；不在每次递归、每条依赖或每次乘加中调用系统内存接口、全局预算锁或命中统计。正常无压力时不预扫所有依赖、不回收热数据、不做 ID 压缩或分页转换。

总预算必须预留最小计算批输出和存储线程取数、编码、提交及回读所需的进展空间，不能全部被数学缓存占满。后台在自己的缓冲额度内主动取数；实际输出超出预估时，在下一次计算派发前申请额外额度、缩小后续批或先等待存储进展。压力不会把克隆、组批或交接责任转回计算线程。若单个结果的必需空间仍无法容纳，应明确报资源不足，不能无限等待一个存储线程无法取得进展的提交。

### 回收顺序

1. 释放已经执行完且不再需要的计划块、失效目录、旧取数缓冲和其他无用临时数据。
2. 淘汰已提交、当前任务不使用、历史复用较低的完成结果；不能有无用数据可释放时主动制造未来 L2 回读。
3. 若主要占用是未执行计划，才将冷的连续计划块交给后台整块溢写。
4. 若尚未提交的数据或当前任务占用了剩余额度，在批次边界等待存储线程自行取数并提交，或缩小后续任务批。

命中热度、近期访问和回读次数以结果页/批次为决策粒度，利用原有查询复用记录和压力路径的批次准备累积；确需采样时单独验收其成本，不默认在正常数学循环中插入每次计数或采样判断。统计是策略估计，不伪装成精确逐项命中率。

存储线程的取数缓冲初始容量是软目标，允许在统一预算安全余量内增长；已完成但尚未提交的数据连同后台副本始终按字节受限。存储缓冲暂满时，计算可继续在正常数学 L1 中完成并标记结果；只有总体内存无法安全容纳下一计算批时才在计算批次边界背压。副本额度由存储线程在取数前取得，包含必要的延寿元数据。

### `Vec<Q>` 的内存下限

活动计划中的整数 ID、连续结果表和数学查找映射保持稳定。单个 `Vec<Q>` 不能释放中间槽位的容量；当前只在既有源借用和耐久条件允许时整体回收，不能把预分配零槽或已换出值当作完成的数学零值。

结果槽、实际有理数负载、数学索引和反向目录均须计入常驻工作集。此前设想的逐槽淘汰、旁路驻留位、代际压缩及固定大小值页不纳入本轮实现。若实际生产任务受这一底座限制，另行评估后端设计；当前不承诺通过继续压低预算解决。

## 6. L2 回读与计划溢写

常驻 L1 命中直接走原数学索引，不询问存储线程。新建空库、当前实例没有淘汰历史值时，不做逐节点 L2 试探。

原有廉价公式和直接判定继续按原算法处理，不为避免微量计算先等待 SQL。后台是否存在历史数据，不能变成对每个新节点同步试探数据库的理由；按需恢复必须证明能减少重算并限制读取放大。

对于重启恢复、确实淘汰过的值或可能存在历史结果的发现前沿，收集一个批次交给后台查找。命中的已提交值装回数学 L1，未命中的才展开；避免每个递归节点一次同步请求/响应。

在压力路径中，每个求值批开始前收集、补齐并固定需要的依赖与项块，再分派工作。算术循环继续读不可变切片，批内不执行 SQL。若工作集过大，缩小调度批；单方程仍无法准入时，应报告资源不足。本轮不增加独立的有界合并或分段求和执行器，也不通过任意切断项块而丢失代数合并机会。

未执行项块沿用原 `TermBlock` 的连续批次结构，以块 ID 和区间定位，只有出现压力才使用独立的工作区存储。SQLite 操作也由存储服务处理，不创建每节点一行的默认 TEMP 执行器。

第一轮诊断必须确认原 OOM 发生在建图还是求值。如果未完成计划主导峰值，结果淘汰不能作为其解决方案。若建图耗时也需要断点恢复，再为已提交计划段及前沿定义单独恢复格式和验收；在此之前只承诺已提交积分成果的恢复。

## 7. SQLite 与兼容性

完成值使用按规范数学键组织的 SQLite 表和精确二进制有理数，保持已有合法 `st`/`ic` 以及回退前 `faber_values` 数据的兼容读取；兼容适配按第 1.2 节区分真实积分、C 归一化和辅助递归约定。回退源码不删除用户数据库。缓存命名空间只在数值语义变化时调整，不绑定普通发布版本。

积分、图层、公式表等使用各自的对象类型和字段格式，复用同一存储服务、总预算与错误传播机制；查询策略、编码粒度和保留策略按类型决定，不强制逐条标量化。

单个存储线程拥有连接，负责键编码、批量查询、排序、插入、WAL/FULL 提交和错误处理。批量提交以行数、字节数、时间及显式屏障共同触发；参数从少量有因果证据的测量中选择。

计算需要的数学索引继续属于计算器；SQLite 的存储索引和持久化业务属于后台。必要的缺页等待与资源不足时的背压不能被称为零成本。异步线程仍共享处理器、内存带宽和分配器，必须通过控制组量化干扰。

## 8. 分阶段实施与验收

以下保留原分阶段设计及验收依据；2026-11-09 起，不再将不断降低预算或扩大开发机规模列为交付前置条件。当前范围和已知限制以第 1.6、9 节为准。

最终目标是常驻模式下无可稳定辨识的明显回归。撤回此前“计算可慢 5%、查询可慢 10%”的放行条件；阶段对照用于定位新增成本，不分别获得可累加的减速额度。

所有阶段均与未经改动的 v0.3.0 生产基线比较，最终组合也必须重测。暂以 2% 作为严格回归复核线，而非可支配的成本预算；需要结合基线噪声及重复配对结果判断。先做三组交错配对，报告每次结果、中位数和离散程度；证据不足时只少量追加，仍不能分辨则结论为不确定，不放宽门槛或选最快一次宣布通过。诊断采样与生产计时分开。

| 阶段 | 内容 | 进入下一阶段的条件 |
|---|---|---|
| A：基线与内存分类 | v0.3.0 公共入口，固定 24 线程；采用已授权且可安全完成的小样本做受控诊断 | 明确内存增长阶段和计划、索引、完成值、临时空间的构成；实际内存与估算分开 |

| B：读取口与完成标记 | 同一核心，计入安全读取口、源生命周期、完成目录和标记的全部改造；后台不取 Q | 单独通过严格回归门槛；所有权重组和串行适配不能当作新的免费基线 |

| E：恢复与生产条件 | 小样本在根答案产生前、后代已有提交时强制终止；注入写入/提交失败和存储线程退出；实际规模由用户在生产环境另行验证 | 已提交且再次访问的积分可复用；故障唤醒等待方并报错。生产条件及资源记录单独报告，不据小样本推定任意预算下可完成 |

分别报告“数学结果可用/普通调用返回”“明确要求的持久化完成”“进程退出”三个时间边界，以及整个实际业务序列的耗时。普通返回允许后台继续工作是显式异步契约，不能据此把必要排空时间藏掉；若完整会话仍出现明显回归，也不能宣称整体优化已经达标。

A/A1/B/C1/C2 使用相同输入、线程、构建配置和起始数学缓存状态；C2 从空数据库开始。每一步以及完整组合均相对 A；相邻阶段只用于定位成本，不用于重置允许回归的基线。直接公式和极小查询同时报告绝对新增延迟及批量吞吐，不能用一次微秒计时的百分比掩盖或夸大问题。

A 的诊断预设实际进程内存和系统剩余内存边界，逼近边界便在安全批次停止，记录阶段、构成和增长趋势；不以再次触发系统 OOM 为诊断方法。实际生产运行由用户在确定约束下执行，分别说明系统可用内存、操作系统进程限制和程序配置额度，并记录包括运行时与后台在内的实际工作集/私有提交峰值及预留余量。

对照依次比较原版、仅完成标记、后台主动取数和完整后台持久化；保持同一计算核心和数据读取布局。跨查询采用不同但共享后代的输入，例如连续两个亏格；相同根答案命中不能代替它。崩溃测试必须发生在最终公共结果产生之前。

每个接入阶段覆盖少量并行大计算、单线程小计算、公式捷径和高命中查询；连续不同查询还比较整段总耗时与重算次数。已知内存不足时的外存路径和崩溃恢复另验收安全、精确结果及可完成性；原版在相同限制下 OOM 时，不伪造可比较的完成耗时百分比。

数据范围验收覆盖串行/并行、直接公式和混合入口：先计算 λ 或 κ 混合查询，再请求其中实际已访问的纯 ψ 或 C–ψ 子积分，验证 L1 复用及重启后的 L2 复用；单独确认 C/ch/λ 归一化、零值和含零次标记的键语义。结构对象逐类验证整块读回、跨查询复用和实际收益；每接入一类，都复测积分主线，防止低优先级写入拖慢核心计算。

强制终止测试不经过正常 `flush` 或析构。多实例测试还需确认，一个实例的写入背压或故障不会使另一实例永久等待。故障传播与耐久保证不能只靠正常返回的重开测试验收。

线程数先保持原来的 24；只在明确发现处理器竞争后，针对相邻档位单独测量。队列、提交批次、页大小也遵守同样规则，不再进行没有因果目标的参数大扫。

### 8.1 需要实验确定的决策

以下实验选择实现细节，不重新开放既定架构边界。计算线程不复制/交接持久化结果、不逐节点查询 SQLite、不统一替换执行器、保留常驻 L1 与原并行能力、保存全部要求范围内的完成积分，以及 WAL/FULL 和显式耐久确认，均不是用跑分快慢取舍的项目。同步发布、合法零值、身份完整性、提交后才淘汰和故障唤醒须做正确性检查，不存在允许错误以换吞吐的候选。

| 次序 | 待定细节及权衡 | 最小实验与观测 | 决策依据 |
|---|---|---|---|
| M0：前置诊断 | 保留直接结果表是否足够，还是计划/索引先成为内存瓶颈 | 在已授权小样本的建图、求值和释放边界分类记录实际内存、容器容量、大整数堆及临时峰值；接近安全边界即停 | 区分常驻下限与可溢写项块，不预设 OOM 全来自已完成结果；值表和目录分页不纳入本轮 |
| M1：结果读取口 | 共享读取所需的所有权/访问边界，及新增结果保留的成本 | 原版、最小安全适配加完成标记、同源后台取数但不编码/写盘逐步对照；并行结果表、串行 memo、公共直接公式分别测，覆盖小查询和高命中 | 单独通过 B/C1 门槛。原来不入 memo 的合法完成结果也要有可拉取结果源，其新增保留与索引成本不能遗漏或靠缩小必存范围规避 |
| M2：数学身份目录 | 后台增量读取已封闭分片，或延寿已有 `Arc<Vec<State>>` 批；索引竞争与元数据延寿互换 | 先证明各候选不会漏掉新增 ID，再对照后台 CPU、索引写入等待、每 ID 额外字节和状态批存活峰值 | 选择能完整覆盖且不拖慢计算、占用较小的方案；不能假定 BTree 新插入键都在已有游标之后，不允许反复扫描全部历史索引 |
| M3：后台采集 | 取数窗口、批大小与唤醒频率；摊薄开销与写回延迟互换 | 固定其他条件，仅比较少量相邻窗口；记录复制字节、持读时长、计算写回等待、后台 CPU、dirty 增长及空闲唤醒 | 先满足计算回归门槛与后台持续进展，再选成本较低者；首选后台小批复制后解锁，只有证据指向它才试存储侧直接编码 |
| M4：缓冲和写批 | 后台副本额度、事务行数/字节数/时间触发；提交摊销与积压、收尾时间互换 | 采集不变，依次调整缓冲与事务阈值；测结果产生/提交字节速率、后台 CPU、提交耗时、全部 dirty 峰值/年龄及最终排空 | 缓冲用来吸收突发，不用来掩盖持续存储吞吐不足；在主线无明显回归、内存安全下选较小的足够配置，三种完成时间全部报告 |
| M5：存储服务调度 | 缺页回读、dirty 提交、计划块和可选结构的服务粒度，以及 WAL checkpoint 的执行时机 | 正常计算叠加受控回读/压力请求；记录回读等待、提交停顿、WAL/磁盘增长、dirty 积压和各源进展；仅在维护成为热点时比较 checkpoint 安排 | 解除计算阻塞的请求及时得到服务，提交也不被读请求或大对象饿死；选择有界服务粒度，不额外占用结果源锁，不降低耐久模式 |
| M6：内存警戒 | 警戒线、回收目标、采样间隔、计算/存储进展预留；可用容量与超调风险互换 | 在预先选定的合理预算范围观察最大批次增长、并行临时峰值、实际内存超调、回收频率和停算时间；包括多源和大有理数 | 根据突发增长及采样滞后确定初值与滞回；样本峰值不是安全证明，不继续收紧预算来迫使所有输入完成 |
| M7：淘汰策略 | 源/批次粒度的近期使用、复用频次及回读记录；统计开销与误淘汰互换 | 在相同合理预算下跑不同但共享后代的连续查询，对照少量粗粒度策略；测策略维护、实际释放量、回读字节、重复回读和整段耗时 | 以低维护成本和减少整段等待为准；原版没有的统计不能当作免费已有能力，不为精确逐项命中率侵入数学循环 |
| M8：L2 恢复 | 发现前沿查找批量及预取范围；请求摊销与无用读取/挤出热数据互换 | 同一计算分别从完整历史库、部分历史库和大量无关历史数据启动；比较按需批读与有限相邻预取，观测恢复耗时、有用/无用字节、峰值和后续回读 | 新空库无逐节点试探，常驻命中无 L2 请求；已提交且再次访问的成果不重算，选择总恢复成本更低且读取放大受控者 |

M1 是可行性实验，不是普通调参。`Planner::node` 的部分公式直接返回 `Operand::Constant`，不能假设它们已在可共享的 L1 槽中；栈上或即将被消费的 Q 也不能直接供后台读取。若安全结果源只能靠计算线程为存储额外克隆 Q、另建待写值容器或替换原执行器才能实现，应判读取口设计需重做，不能仅因跑分快而放行。

M2 优先复用现成的不可变状态批；只有状态延寿或目录竞争已成为瓶颈，再比较另一种正确的增量定位方式。M3 的短读取窗口、M4 的副本缓冲额度与事务大小是三个独立参数，小窗口可以累积成大事务，不得绑定成一个统一的“批大小”。空闲轮询/通知退让、缓冲复用也只在出现空闲 CPU、发现延迟或分配热点后追加对照。

此前设想的值页和安全代际回收实验不再继续。以下四项只在实际生产证据触发后另行讨论，本轮不同时展开：

- **计划溢写**：未执行计划确为主要占用时，比较连续块大小和压力下调度批大小；测真实释放量、重读放大、补齐等待和吞吐，保留整方程代数合并。
- **编码与数据库组织**：后台键生成、编码或数据库读写成为热点后，才比较少量精确二进制布局、批内排序/去重和 SQLite 缓存配置；计入数据库/WAL 体积与恢复解码成本，不新增哈希或校验机制。
- **结构对象持久化**：积分主线通过后，每类只比较重建、首次保存和后续载入，按完整会话收益决定启用范围与块大小；不能用第二次命中收益掩盖主线首次写入的明显回归。
- **计算线程配额**：默认保留计算线程上限 24 和一个存储线程；只有观测到处理器竞争才比较邻近计算配额，记录整段吞吐与后台积压，不预先为存储减少计算并行度；最终仍对照原版相同的线程上限，不能重选较慢的原版配置掩盖回归。

普通返回不自动等待落盘已经确定；若要增加严格的最大未提交损失量或最长未提交时间，这是调用者的恢复策略选择。用户内存上限、临时溢写的允许范围/磁盘额度、哪些可选结构要求显式耐久也属于策略边界。实验只能在这些边界内报告开销和实际重算代价，不能因为某个设置最快而自行放宽恢复承诺，也不能把定时触发提交误称为整个 dirty 积压的严格时间上限。

### 8.2 最小实验次序

原首轮依次进行 M0、M1、M2、M3、M4，确定内存根因、安全读取口和后台持久化的成本，结果见第 8.3 节。当前收缩后只按第 1.6 节做有限的小样本复核，不继续扩大规模或收紧预算扫描。每轮只改变一个相关因素，使用少量候选；锁/采集问题先在 C1 隔离，真实 I/O 成本留在 C2，不用单独的 SQLite 写入跑分代替完整计算。

代表性负载包含并行 Hodge 计算、串行/混合积分、直接公式、高 L1 命中和连续不同查询；小复现用来筛选，g=15 等原版可安全完成的规模复核候选，受压与强制终止恢复另行验收。探针放在后台和已有批次边界，诊断与生产计时分离；不在每条依赖或每次乘加中加计时/计数，不生成新脚本或数据档案。最终仍按本节原定的配对对照与完整收尾规则验收。

|---|---|---:|

| 表示 | 目录容量/载荷 | 后台线程 CPU（复测样本） | 目录收尾（复测样本） |
|---|---:|---:|---:|

| 连续字节区加偏移表 | 80.00 MiB | 0.281250 s | 2.442 ms |

**M3：先用短睡眠退让和小窗口。** g=15 同一 64 KiB 窗口下，遇写回时 `yield` 重试约 251 万次，后台 CPU 约 1.156 s；50 µs 睡眠退让约 1,361 次重试、CPU 约 0.438 s。计算写锁累计等待分别约 2.435 ms、0.777 ms；这仅量化锁等待，不能代表全部后台干扰。

g=14 又做了 16/64 KiB 三组对照，均完整复制 961,550 项。16 KiB 约需 4,949 次读取窗口，64 KiB 约 1,394 次；两者 CPU 中位数均约 0.250 s，累计写锁等待中位数约 0.363/0.969 ms，总耗时没有稳定优势。先采用 64 KiB、短睡眠退让作为初值，保留 24 线程；不将它们称为通用最优参数。睡眠实长受操作系统调度影响。

### 8.4 根据测量确定的实施计划

已有证据足以开始分阶段实施；尚不足以宣布完整方案通过性能验收。将未执行计划块的压力溢写列为首版必要能力，仅在真实压力下启用；完成积分持久化与计划工作区后备分别验收，共同覆盖恢复和内存目标。当前没有证据要求先改连续结果数组的布局。

| 次序 | 实施内容 | 完成条件 |
|---|---|---|
| 1：长期结果源 | 将实验读取口接入真实生命周期，保留原数学索引、连续结果表和调用线程并发；补齐串行 memo、公共入口及直接公式的完成结果源，覆盖纯 ψ、λ、κ/ch 混合及合法零值 | 查询结束不丢失可复用后代；后台不持有整张计划；计算只正常写回 L1 并标记完成，不为存储复制或打包 Q。相同生产公共入口通过 A1/B 对照 |
| 2：单存储服务，不写盘 | 将身份发现、连续字节目录和结果读取接成同一个服务；按完成目录增量拉取，限制原状态批延寿。初始使用 64 KiB 读取窗口、短睡眠退让，保留计算线程上限 24 | 覆盖全部新增身份和完成值；没有历史全表反复扫描；实际源生命周期、扩容和跨查询运行通过 C1。原型中位数不能替代此项验收 |
| 3：SQLite 持久化 | 后台自行完成规范键、精确有理数编码、批量查询与 WAL/FULL 提交；接入显式 flush/close、连续提交水位及异步错误传播 | 所有要求保存的完成积分均可重开复用，兼容旧数据语义；普通调用不等待落盘。依次测定副本额度及事务字节/行数/时间阈值，报告数学返回、耐久完成和会话退出耗时，通过 C2 |
| 4：统一预算与压力路径 | 接入实际可用内存、私有提交和多实例总账；为计算、取数、提交及回读预留进展空间。释放无用块、回收已提交冷结果，并支持未执行连续项块的有限整块后备和按需补齐 | 以已授权小样本定向测实际释放、扩容超调、回读放大和等待。保留整方程合并，常驻算术循环不增加分页或 SQL；预算不足应明确报错，低预算长时间规划仍属已知限制 |
| 5：恢复与生产条件 | 在根答案产生前、已有后代提交时强制终止并重启；覆盖部分历史库、故障和多实例。生产规模及预算由用户在生产环境验证 | 已提交且再次访问的成果可复用；未提交批和未保存的建图进度可重做；故障唤醒等待方。报告实际系统余量、程序额度、进程峰值及三个时间边界，不新增开发机大规模验收任务 |
| 6：可选结构对象 | 积分主线通过后，按第 1.3 节逐类接入完整图层、符号多项式等高价值对象 | 每类均证明重建/保存/载入的完整会话收益，并复测积分主线；不以扩展这些对象替代前述内存目标 |

步骤 1–3 在原版可安全完成的规模上逐步检验新增成本；步骤 1 中串行和直接公式的长期结果源仍是可行性门槛，不能由并行原型替代。步骤 4 必须在建图过程中、完整计划形成前就能释放未执行块，同时覆盖求值；另测溢写后仍常驻的层、索引和依赖元数据下限，不能只证明结果淘汰有效或假设项块落盘足以保证目标规模。计划后备沿用原不可变项块及整数引用，存储线程处理块读写，恢复时仍可重建未保存的计划；不引入每节点数据库执行器。若某一步不能满足原计算流程和性能边界，先修正该步，再叠加后续机制。

剩余参数随对应实现测定，无需在实现前穷举：长期结果源的端到端成本在步骤 1–2 检验，写批与存储调度在步骤 3 测定，警戒/回收/溢写粒度及预取在步骤 4–5 测定。所有比较继续以 v0.3.0 为统一基线，不累加各阶段的减速容忍度。

## 9. 本轮交付范围

生产实现已接入长期结果源、单 SQLite 后台服务、进程共享内存预算和压力工作区。当前开发验收以本机小样本回归为准；更大规模及约 50 GiB 的生产运行由用户在生产机执行，不作为开发结束的前置条件。此前未完成的 g=18 受压诊断和 g=20 测试均已停止，不算成功验收；2026-11-08 曾按用户逐次指定运行 g=16、g=17 和 g=18，历史耗时保留在第 10 节。2026-11-09 的范围收口不再新增同类大规模测试。串行/并行后代、纯 ψ、归一化 C、实际 κ/ψ/λ/ch 混合积分以及 DR、Witten、Chiodo、Hyperell/Biell 标量入口均保存完整数学身份与精确值；合法零也保存。完整图层和符号多项式属于后续可选范围。

这里覆盖实际调用的积分入口和已计算的叶子、规范后代。Tau 的 dilaton/string 别名可由已保存的规范后代及精确因子廉价还原，不要求每个别名各占一行。图上的度数剪枝未调用积分后端，不为这类分支额外生成零值记录。

正常计算只写原数学 L1 并发布完成位置；后台构造身份、编码和提交。并行后代的后台读取口直接借用原连续结果表，按 64 KiB 窗口编码，不再克隆 Q 或逐条创建身份向量。当前默认计算线程上限为 24，压力求值组上限为 1024 条、额度不足自动缩组；提交阈值为 16,384 行/100 ms/8 MiB，使用 WAL/FULL。`flush`/`close` 确认已发布目标的提交；异常终止可复用已提交积分，未提交窗口和未持久化计划可能重做。临时计划工作区可以丢弃，不承担数学结果的持久性。

内存监视器独立于 SQL 线程，每 100 ms 观测进程私有用量、系统可用空间及可见环境限制。预算共享于进程中的所有会话，默认预留 1 GiB 系统余量及 256 MiB 进展空间，警戒/回收比例为计算额度的 85%/70%。已提交结果按粗粒度命中比例选源回收。建图和求值都可进入整块磁盘后备；保留整方程合并。块在有余量时驻留，按需回收，缺页只由后台读取。批次预留是保守工作估计，不能把它描述成任意大整数表达式的严格 RSS 上界。

本轮保留稀疏方程标量表示，将 `PackedEquation` 目录项从 136 bytes 降到 40 bytes（本机 64-bit）；准入先记实际需要的元数据，再在分配前补足解码和输出额度，并保留总账安全约束及有界重试。GNU Linux 的压力巡检可尝试归还分配器空闲页，之后重新采样；返回值不作为新增额度或回收进展证据。规划完成后清空数学索引的实验已撤回，原键到 ID 的查找映射继续服务跨查询复用。活动结果表和反向目录保持常驻，不扩展为通用外存后端。

回收补丁将活跃 Registry 内的回收许可细化到结果源：并行源在整次 `with_engine` 期间持有 `RwLock<()>` 读许可，后台仅尝试取得闲源的独占许可；没有跨期整数 ID 的 map 源依赖原 `try_write`，并在锁内重新核对 durable 水位。重新开放被回收源之前先发布 history 状态。活跃并行源仍保留整张连续结果表和数学索引，不支持清除旧 ID 前缀或逐项回收；同一源连续查询也不保证在调用间隙完成回收。该版曾通过 355 项 Rust 单元测试；随后稀疏历史恢复修复的验证记录见本节末尾。

后代前沿批读使用单个只读快照；仅在确认旧正 C 别名命名空间为空时，利用当前 ranked 键的首尾边界跳过必然未命中及多余的兼容点查。提示每批重建，不跨批保留负缓存；存在旧别名或提示读取失败时保留精确兼容读取及其错误语义。`StorageReport.read_keys` 统计逻辑请求数，包括由提示排除的请求，不等于实际 SQL 点查次数。

Rust 使用 `socle::set_cache_memory_limit(Some(bytes))` 配置进程上限，`None` 恢复自动预算；Python 使用 `FABER.set_memory_limit(maximum_bytes=...)`。`CacheSession` 和 Python 实例各自绑定数据库，可显式 `flush_cache`/`close_cache`。缓存打开或持久化失败明确报错；Python `cache=""`、CLI 不指定 `--cache` 时使用纯内存模式。

临时工作库采用 64 KiB 页、约 2 MiB 页缓存和唯一后台连接的 SQLite EXCLUSIVE 模式；每个逻辑块用单个有序游标流式读取。此设置只作用于新建、可丢弃的工作文件；主结果库保留原 WAL/FULL 和多实例访问方式。512 MiB/g=12 的页大小对照为 4/16/64 KiB：13.08/7.93/8.01 秒；1.5 GiB/g=15 对照 16/64 KiB：144.20/137.93 秒，均与旧版精确值一致。页缓存仍以字节限额配置，没有通过放大内存缓存换取结果。

实现文件遵守 Rust 源码约束；唯一 Python 测试变更是已单独批准的实例隔离断言。不引入新脚本、JSON/JSONL/TSV 数据档案、哈希索引或额外的校验、证书、冻结机制。本文和审查归档是本次明确要求保存的文档。前文原型数据保留为设计依据，不代替本轮生产验收。
