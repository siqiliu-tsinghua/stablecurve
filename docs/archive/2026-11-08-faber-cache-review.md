# v0.3.0 之后的 FABER 缓存改造审查报告

归档日期：2026-11-08（Asia/Shanghai）。

本报告记录回退前的审查结论。审查范围包括 v0.3.0 之后首次缓存改造提交及当时尚未提交的修改；本文所指代码位置属于回退前工作树，回退后相应文件可能不再存在。本轮审查为只读审查，没有运行新的重型测量。

## 总体结论

改造把“给原有计算器补上可靠、有界的二级缓存”，扩大成了“重写一个通用可溢写执行器”，随后又不断优化这个新执行器的额外成本。这个方向偏离了目标。

应该保住的核心行为是：数据常驻内存时，继续享有原来的计算效率和跨查询复用；完成结果在后台持久化；内存压力出现后，才承担淘汰、溢写和回读的成本。

## 已确认的问题

### 1. 原来的高效计算路径被无条件替换

v0.3.0 已经有连续求和块、整数 ID、直接访问的 `Vec<Q>` 和分层并行。改造后的生产入口 `hodge/psi.rs` 统一进入 `managed`，包括单线程和不启用持久缓存的情况。

无持久缓存时，`managed::Work::finish_batch` 还会无条件把工作图放入 SQLite TEMP，并编码保存结果。实际是否产生磁盘 I/O 取决于 SQLite 的缓存情况，但内存充足时也进入数据库工作区，是代码明确规定的行为。这直接违背了目标。

### 2. 增加 L2 的同时，破坏了跨查询 L1 复用

原版的数学索引和结果表会保留下来，后续相关查询可以继续使用。

改造后的持久模式只把完成后代结果提交给存储队列，没有完整进入共享 L1；查询结束又清掉本次 `Work` 的索引和值。下一个不同查询即使内存充足，也可能重新等待 SQLite 读取刚算过的后代积分。

这些值并非因内存不足被淘汰，而是被查询生命周期主动清掉。重复同一个完整查询很快，只能说明顶层答案命中，不能证明后代积分仍保留在 L1。

### 3. 受限内存机制进入日常计算路径

逐方程分块、带锁的块索引、共享引用、最后使用层和配额记账，都增加了常驻路径的成本。图、项块、索引和稠密结果表又分别受到固定比例限制。

例如，图记录达到预算的五分之一就可触发溢写，不要求总体达到内存警戒线。因此实现允许“总内存还有余量，某个固定分区先迫使计算变慢”。是否以及何时在 g=20 触发，尚无对应阶段和实际进程内存证据。

分块和预算应围绕原有批次、连续块和实际内存压力设计，而不应成为默认的逐节点成本。

### 4. 部分原有算法优化被分块方式削弱

原版先对整个方程合并重复项、消去抵消项，再装入连续块。改造后达到 2048 项便提前存块，最后的 `collect()` 只能处理剩余尾部。

精确有理数使这些分开累加仍可得到正确结果，但跨块合并、抵消的机会已经丢失，可能增加某些大方程的算术工作量。影响尚未量化。因此不能把差距笼统归为“管理开销”，计算组织本身也发生了变化。

### 5. 最初的 OOM 根因没有充分确认

应先区分三类内存：

- 已完成积分的缓存；
- 尚未求值的方程、求和项和依赖计划；
- 并行临时空间、待写队列及其他运行时占用。

既有 g=15 测量中，求和项约占 1138 MiB、方程约占 391 MiB，说明计算计划本身就很大。但在没有确认 g=20 被杀时所处阶段及各部分占比之前，就推进了整套执行器改写。

后代结果未持久化确实是缺口；它是否解释 OOM 的主要部分，需要直接证据。持久化完成值、限制计划峰值、恢复未完成计划，应分别说明。改造后的 TEMP 计划是可丢弃的，崩溃后仍需重建，不能把完成值可复用描述成整个计算现场无损接续。

### 6. 性能结论口径不充分

“仍慢约 37%”来自当前源码中两条测试路径，并非两个对称的生产构建。即使关闭探针采集，测试构建仍保留探针调用，而两条路径的调用数量不同。该数值不能作为精确生产回归幅度。

此前 CLI 对照中的“旧版”也是第一次缓存改造后的版本，并非 v0.3.0。因此“比旧版快约 21%”只能证明后来修补有收益，不能证明恢复了原版效率。

队列等待几百毫秒，不能证明后台存储只造成几百毫秒影响；CPU、内存带宽和分配器竞争尚未隔离。账面预算没有越界，也不能替代真实进程内存测量。

## 应保留与重做的部分

值得保留的能力包括实例隔离、精确二进制持久化、后台批量事务、有界队列、失败传播及编码缓冲区复用。这些能力应作为独立设计参考，不应迫使新执行器成为默认计算路径。

需要重做生产计算器与缓存管理的边界：以 v0.3.0 的连续存储、直接结果表和数学索引为基础，恢复同实例跨查询 L1 生命周期；把记账和交接尽量放在批次边界；由真实压力触发额外处理。可溢写执行器是否保留为低内存后备路径，应由内存分解和对照测量决定。

## 后续设计与验收要求

1. 先查清 OOM 内存构成及发生阶段，分别决定完成值淘汰和未完成计划的处理方式。
2. 以 v0.3.0 生产构建为基线，保持同一数学核心，分离交接成本、后台编码与 SQLite 成本、工作区管理成本。
3. 区分结果可用、持久化完成和进程退出三个时间边界。
4. 覆盖空数据库且内存充足、同进程不同但共享后代的查询、实际内存压力、部分结果恢复。
5. 同时记录实际进程内存与受管内存估算；数值测试和预算断言不能替代性能及 OOM 行为验收。
6. 异步批量写存在已接受的有界未提交窗口。成功返回前的提交保证、已提交完成值的可复用性，与未完成计划的恢复能力必须明确区分。

此前把“比上一次快”和“数值测试通过”当成了优化接近完成的依据，而常驻性能、跨查询 L1 复用和内存压力行为没有得到完整验收。这是本次改造过程需要纠正的核心问题。
